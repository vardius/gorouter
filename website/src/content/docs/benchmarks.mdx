These numbers measure the router alone: handlers and middleware do nothing, so what's left is the cost of matching, params and dispatch.
Your handlers will dominate a real request; the point is that the router adds as little as possible.

The biggest gains are behind middleware: v4 composed each route's middleware chain on every request, v5 composes it once at registration.
On fasthttp, v5 also stopped allocating for params, 404s and literal routes.

<Aside title="Where net/http allocates">
On `net/http`, a route with a few params allocates twice: that is `Request.SetPathValue` storing the values so `r.PathValue` can read them.
Storing them that way also makes a one-param route a few nanoseconds slower than v4, the price of reading params with the standard `r.PathValue`.
The matching itself allocates nothing, and neither do literal routes, middleware chains or finding no route. A 405 allocates its `Allow` header value, and a mount one copy of the request, as `http.StripPrefix` does.
</Aside>

## Run them yourself

From a clone of the repository:

```sh
go test -run '^$' -bench . -benchmem ./...
```

To compare two versions, run each a few times and compare with [benchstat](https://pkg.go.dev/golang.org/x/perf/cmd/benchstat):

```sh
go test -run '^$' -bench . -count 10 ./... > new.txt
benchstat old.txt new.txt
```

The allocation counts are also enforced by tests: `TestAllocations` in each router package fails if a request allocates more than it should.
